# NeighborhoodOS: Data Stewardship and Governance Guide

> **"Data stewardship is a human responsibility, not a database setting."**

This guide outlines the governance rules, steward roles, data deletion workflows, and audit procedures for any NeighborhoodOS node. Under our core safety commitments, we establish clear human accountability to manage and protect our public-interest datasets.

---

## 👥 The Data Steward Role

Every dataset synced or generated by a local NeighborhoodOS node must have a named, human **Data Steward**. This role is a volunteer or partner representative (such as a KC Digital Drive staffer or neighborhood organizer) who is responsible for the integrity and safety of that data.

### The Steward's Key Responsibilities:
1.  **Data Quality Audit**: Review incoming datasets weekly to ensure they match reality (e.g. flagging duplicate 311 complaints or obsolete housing violations).
2.  **PII Redaction**: Proactively inspect text fields (like 311 comment blocks or legislative notes) to identify and redact any accidentally submitted Personally Identifiable Information (such as phone numbers, emails, or personal names).
3.  **Data-Subject Requests (DSRs)**: Handle requests from residents who want to review, redact, or delete data points related to their properties.
4.  **Changelog Review**: Author and sign off on a weekly plain-language summary of dataset changes before publishing it to the community.

---

## 🛡 The Data Deletion & Redaction Workflow

Under our **Civic Memory Safety Doctrine**, residents have an absolute right to privacy and redaction. If a resident requests that their property's 311 or permit history be redacted from the public view:

### 1. The Redaction Protocol
- The resident submits their request to the local Data Steward (either in-person during a Workshop clinic or through a secure email form).
- The Steward verifies the resident's relationship to the property (ensuring they are the tenant or homeowner, not a commercial investor looking to hide public records).
- The Steward executes the redaction query directly through our secure interface.

### 2. SQLite Redaction (Hard-Deletion)
Unlike corporate databases that "soft-delete" records (keeping them hidden but stored on backup servers), our SQLite database performs a **hard-delete and vacuum** to completely purge the data from disk:

```sql
-- 1. Hard delete the specified property record
DELETE FROM requests_311 WHERE street_address = '1234 Target St' OR case_id = 'XYZ-999';

-- 2. Purge unused database space and overwrite deleted bytes
VACUUM;
```

## 📊 Auditing and System Integrity

Every administrative action, dataset import, and safety block must be auditable by the public.

### 1. The Append-Only Audit Trail
Our secure database proxy driver (`core/db.js`) automatically writes every schema edit, query execution, and security block to the `system_safety_audit` table. This table is strictly append-only. 
- *Rule*: No database operator or administrator may edit or delete rows in the `system_safety_audit` table. This ensures complete transparency.

### 2. Weekly Security Sweep
The Steward must run our security sweep tool weekly to inspect the `system_safety_audit` table for any blocked safety violations. If an un-audited script or developer tried to execute a prohibited query (like querying `resident_score`), it will show up as a `BLOCKED` event in the audit trail.
- If a critical safety block is found, the Steward must immediately audit the code changes, locate the offending script, and revert it.

## 📋 The Steward's Weekly Checklist

Before publishing the weekly neighborhood memory digest:
- [ ] Have you run the automated PII scanner to check for raw phone numbers or emails in our 311 text fields?
- [ ] Have you processed and executed all validated data-subject deletion requests?
- [ ] Have you run `VACUUM` on the database to ensure deleted bytes are completely wiped from disk?
- [ ] Have you reviewed the `system_safety_audit` table for any blocked safety violations?
- [ ] Have you drafted and signed off on the weekly plain-language changelog?
