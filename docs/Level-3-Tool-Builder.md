# Workshop Manual: Level 3 — The Tool Builder

> **"We don't build software platforms. We build sharp, community-benefit tools."**

This guide is the curriculum and technical specification for our **"Build" Track** (Level 3). It teaches resident-co-designers, community developers, and partners (such as KC Digital Drive) how to take a finalized Problem Brief from Level 2 and turn it into a simple, secure, and accessible local tool using our **Local AI Infrastructure** and SQLite databases.

---

## 🧭 Part 1: The Design Principles of Local Tools

In NeighborhoodOS, we reject the default tech-industry bias toward building massive, complex platforms. We design for simplicity, accessibility, and trust.

### The Five "Local-First" Design Rules:
1.  **The Wedge Rule**: Build the absolute smallest tool that solves one specific, high-priority neighborhood problem. Do not add "feature creep."
2.  **No Automated Actions**: Our tools may only suggest context, organize public records, or draft templates. They are **strictly prohibited** from performing outbound automated actions (like filing a report, sending a message, or making a decision) without a human-in-the-loop reviewing and clicking "send."
3.  **The Kitchen-Table Aesthetic**: Avoid slick, generic SaaS dashboard layouts. Design pages to feel like a warm civic field guide, a local notebook, or a kitchen-table operating manual. (See `DESIGN.md` for our canonical type, spacing, and color palettes).
4.  **Provenance-First (Show the Receipts)**: Every fact, summary, or suggestion generated by a local model must display clear, clickable links back to the original public-record source file.
5.  **Local Database Isolation**: Keep database files small, portable, and isolated in SQLite. If a tool fails or needs to be retired, we should be able to drop its `.db` file without impacting the rest of the node.

## 🛠 Part 2: Step-by-Step Tool Assembly

This is the standard engineering pathway to bring a Level 3 tool to life:

```
[Problem Brief] ──> [Schema Setup] ──> [Local Prompting] ──> [Web Interface]
```

### Step 1: Initialize the SQLite Database
Instead of running a heavy PostgreSQL cluster, create a single, portable SQLite database. Let's look at a typical schema for a *Neighborhood Service Navigator*:

```sql
-- data/navigator.db
CREATE TABLE IF NOT EXISTS city_codes (
  id              TEXT PRIMARY KEY,
  code_section    TEXT NOT NULL,
  summary_text    TEXT NOT NULL, -- Plain-English translation
  municipal_link  TEXT           -- Direct link to official city portal
);

CREATE TABLE IF NOT EXISTS local_resources (
  id              TEXT PRIMARY KEY,
  name            TEXT NOT NULL,
  category        TEXT NOT NULL, -- e.g. 'tenant_advocacy', 'utility_assistance'
  contact_info    TEXT NOT NULL,
  notes           TEXT
);
```

### Step 2: Set Up the Local AI Pipeline
Use our secure database wrapper (`core/db.js`) to handle your queries safely. To integrate a local model (such as `gemma4:e4b`) to summarize a public city code:

1.  **Initialize the Local API Caller**: Set up your Ollama API endpoint securely (locally or over Tailscale).
2.  **Enforce the System Instructions**: Write strict, bounded instructions for your local model:
    ```javascript
    const SYSTEM_INSTRUCTIONS = `
      You are a local civic navigator. Your job is to translate complex municipal codes into plain, kitchen-table English.
      
      Hard Rules:
      - Always link back to the official city code portal.
      - Never offer legal advice or make promises.
      - If you do not know a detail, say "This detail is not in the public database" and provide the city contact phone number.
      - Keep your language concise, friendly, and honest.
    `;
    ```

### Step 3: Design the HTML Interface
Keep the interface lightweight, semantic, and highly accessible:
- Use clear visual hierarchy with डिस्प्ले headings (`Fraunces` or `Georgia`).
- Keep text readable with high contrast against the paper background (`#F5EFE6`).
- Ensure all controls are fully accessible via keyboard.
- Include direct links to the official city sources next to every AI-generated summary.

## 🛡 Part 3: Programmatic Safety Enforcements

Every Level 3 developer must integrate our database proxy wrapper (`core/db.js`) to protect resident privacy programmatically:
- **Blocklist Check**: Any attempt to query or store individual tracking metrics, resident scores, or personal social scraping will trigger a `CivicSafetyViolationError` and halt execution.
- **Join Restraints**: Never attempt to run joins across identity databases (containing user emails or phone numbers) and public records (like 311 complaints or property violations). If your query requires checking eligibility, handle the logic strictly in memory and discard the state immediately.

## 📋 Level 3 Checklist (The Definition of "Done")

Before deploying your tool or presenting it to community partners:
- [ ] Does the tool pass the **Red-Light Test** in `PILOT-RUBRIC.md`?
- [ ] Are all database operations wrapped in the secure driver (`core/db.js`)?
- [ ] Is there a clear, clickable link to the original public-record source for every fact?
- [ ] Has the tool been reviewed and tested on a mobile device to ensure visual contrast and layout accessibility are green?
- [ ] Is there a human-in-the-loop review step for any outbound action?
